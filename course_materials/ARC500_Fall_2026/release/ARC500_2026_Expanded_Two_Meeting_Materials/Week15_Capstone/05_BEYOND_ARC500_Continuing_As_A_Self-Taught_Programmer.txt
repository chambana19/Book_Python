ARC 500 · BEYOND ARC500: CONTINUING AS A SELF-TAUGHT PROGRAMMER
Syracuse University · School of Architecture
A capstone handout for the end of Week 15 — read this after your presentation, not before.

WHY THIS EXISTS

Every other handout in this course ends with an instructor in the room, a
rubric, and a due date. This one doesn't. From here on, you decide what to
build, what to check, and when you're done. That is a harder problem than
any single Python skill in this course, so this handout is deliberately
about HOW to keep going, not WHAT to learn next — the "what" branches
differently for every student, and is covered in Section 4.

The single most important thing to carry forward is not a library. It's the
loop you already practiced fifteen weeks in a row: QUESTION -> INPUTS/
ASSUMPTIONS -> METHOD -> CHECKS/INTERPRET. Every skill below is useless
without that loop around it, and every skill below is learnable BECAUSE you
already have that loop.

================================================================
1. WHAT YOU CAN ALREADY DO — A HONEST INVENTORY
================================================================

Read this list and mean it. You are not "a beginner who took a Python
class." You are someone who can, independently:

  - Read a dataset you've never seen before, interview it for
    trustworthiness (shape, dtypes, missing values, provenance), and decide
    what to trust before calculating anything (Weeks 4-5).
  - Group, rank, and flag outliers in real data with two independent rules,
    and write a defensible keep/investigate/exclude decision (Week 5).
  - Choose an honest chart for a specific question and label it so a
    stranger can verify your claim from the picture alone (Week 6).
  - Reproject and join spatial data correctly, and explain why a geographic
    CRS cannot be trusted to measure area or distance (Week 7).
  - Formulate a real decision as variables, an objective, and constraints,
    and solve it three different ways — exactly (linprog), by gradient
    search (minimize), and by heuristic search (a genetic algorithm you
    built from scratch) — and know which one fits which kind of problem
    (Weeks 10-12).
  - Fit a prediction model, refuse to trust it until you've beaten a naive
    baseline, hunted for leakage, and read a residual plot or a confusion
    matrix (Weeks 13-14).
  - Chain a fitted model into a solver as a surrogate objective and state,
    in writing, the difference between "the optimizer's recommendation" and
    "the architect's decision" (Week 15).
  - Use a generative-AI coding assistant without becoming dependent on it —
    accept, modify, reject, and TEST every suggestion, and keep a written
    record of which you did and why.

That is a real, employable, transferable skill set. It is also not close to
everything there is — which is the entire point of this document.

================================================================
2. THE ONE HABIT WORTH PROTECTING: SELF-AUDITED AI USE
================================================================

In this course, your AI-use record was graded. After this course, nobody
checks it — which is exactly when it matters most, because the temptation
to skip the "did I actually test this" step is highest when no one is
grading it.

Keep doing it anyway, informally, forever:
  1. State the question before you prompt. If you can't state it, an AI
     assistant can't help you state it either — it will guess, and you
     won't be able to tell a good guess from a bad one.
  2. Ask for the smallest piece that lets you check something, not the
     whole script. A 200-line AI-generated file you haven't run yet is not
     progress; it's a large unverified claim.
  3. Run it. Read the output. Does it match what you predicted, roughly,
     before you saw it? If you didn't predict anything first, go back and
     predict — this is the single habit this course repeated more than any
     other, in every handout, for a reason.
  4. When a suggestion uses something you don't recognize, stop and look it
     up before you accept it — not after.

ONE NEW WARNING, specific to what comes after this course: everything you
worked with here (pandas, NumPy, Matplotlib, GeoPandas, SciPy, scikit-learn)
is extremely common in AI training data, so AI suggestions about it are
usually solid. The moment you move into more specialized architecture-
specific tools, you are moving into libraries with far less AI training
coverage, more breaking changes between versions, and more code online
that is simply wrong or outdated. Trust AI output LESS in that territory,
not more, and verify against the tool's own official documentation every
time, not just your own test.

3. YOUR FIRST SELF-DIRECTED PROJECT (DO THIS BEFORE ANYTHING ELSE)
================================================================

Before you install a single new tool, run one more project using ONLY what
you already have installed and already know: Python, NumPy, pandas,
Matplotlib, GeoPandas, SciPy, scikit-learn. This is deliberately NOT a new
skill — it's a rehearsal for working WITHOUT a syllabus telling you what
week it is.

THE ASSIGNMENT YOU GIVE YOURSELF:
  Pick one real question about a building, a neighborhood, a material, or a
  design decision that you actually want the answer to. It can be about a
  studio project, a building you walk past, or a dataset you find online
  (a city's open-data portal is a good place to look; many publish
  building-permit, energy-benchmarking, or zoning data as CSV or GeoJSON —
  the exact same formats you've used all semester).

MINIMUM SCOPE (smaller than either course project — that's intentional):
  - One question you can state in one sentence.
  - One dataset, with a provenance note (where it came from, what one row
    means, what units).
  - One cleaning pass with a written decision for anything you dropped.
  - One outlier check.
  - Two figures that answer two different sub-questions.
  - EITHER one optimization (even a two-variable linprog or minimize call)
    OR one small model (even a simple LinearRegression against a mean
    baseline) — pick whichever fits your question, not both.
  - One paragraph: what you'd tell a client or a studio critic, and one
    limitation you'd say out loud before they asked.

Give yourself two weekends, not a semester. If you get stuck for more than
20-30 minutes on one error, that's the signal to go find documentation or
ask an AI assistant a SPECIFIC question about that one error — not the
signal to start over with a different question. Finishing a small project
badly teaches you more than abandoning a good one.

================================================================
4. WHERE TO GO NEXT — BRANCHES BY INTEREST
================================================================

You don't need all of these. Pick the branch closest to what you actually
want to design, and go deep on ONE before sampling the others.

--- BRANCH A: BUILDING PERFORMANCE AND ENVIRONMENTAL ANALYSIS ---
If Weeks 4-9's "data as evidence" and Weeks 13-14's prediction work were
your favorite weeks:
  - Ladybug Tools and Honeybee (open-source, available as standalone Python
    packages) run real EnergyPlus and Radiance simulations — daylight,
    energy, comfort — from Python-scripted geometry. This is the direct,
    real-tool version of the WWR/shading proxy formulas you swept and
    optimized in Weeks 9-12; the "proxy" training wheels come off.
  - Once you're running real simulations, everything from Weeks 4-6 (clean
    the output, group it, chart it honestly) and Weeks 13-14 (don't trust a
    single run, check for leakage in your own workflow, know your model's
    domain) applies directly to simulation results, not just tabular data.
  Where to start: the official documentation at ladybug.tools, and the
  Ladybug Tools forum on discourse (forum.ladybug.tools) for troubleshooting
  — an actively maintained, architecture-specific community.

--- BRANCH B: GIS AND URBAN-SCALE ANALYSIS ---
If Week 7's spatial-join work was your favorite week:
  - Keep building directly on GeoPandas — you already know CRS, projection,
    buffers, and joins. The next steps are larger real datasets (city
    parcel data, transit networks, census/demographic layers) and slightly
    heavier tools built on the same foundations: rasterio (for raster/
    imagery data), networkx (for street-network analysis), and osmnx
    (OpenStreetMap network data, built on networkx and GeoPandas).
  - QGIS's own Python console runs plain Python against the same
    geopandas/shapely ecosystem, if you want a GUI alongside your scripts.
  Where to start: geopandas.org and the QGIS documentation
  (docs.qgis.org) — both are stable, well-maintained references.

--- BRANCH C: MACHINE LEARNING, DEEPER ---
If Weeks 13-14 hooked you:
  - You already know the honest-evaluation discipline (baseline, split,
    leakage, residuals, confusion matrix, model card) that most tutorials
    skip. Use it as your filter: any tutorial or AI-generated ML code that
    doesn't mention a baseline or a train/test split is teaching you to
    build something you can't trust.
  - Natural next steps using tools you already have installed: try
    RandomForestRegressor/Classifier from scikit-learn (still one import
    away, no new library) on a dataset you care about, and compare it
    honestly against your Week 13/14 linear model using the same metrics.
  - Kaggle (kaggle.com) hosts real, messy, free datasets and a large
    community — a reasonable next practice ground, using the exact
    train_test_split -> baseline -> model -> metrics -> residuals loop from
    Week 13.
  Where to start: scikit-learn's own documentation (scikit-learn.org) is
  unusually good and example-driven — read the "User Guide," not just the
  API reference.

================================================================
5. THE TOOLS THAT COME AFTER SPYDER
================================================================

Spyder was the right choice for Week 1 — one file, one console, one
Variable Explorer, nothing to configure. As your projects get bigger or
more collaborative, two things become worth learning on purpose, not by
accident:

  - JUPYTER NOTEBOOKS: closer to what most online tutorials and Kaggle
    examples use; better than Spyder for mixing narrative text with code and
    figures (a research note, a portfolio piece). The `# %%` cells you've
    used all semester are Spyder's version of the same idea notebooks are
    built around — the mental model transfers directly.
  - VS CODE: a more configurable editor once you're working across multiple
    files or languages (e.g., web-based portfolio code), or need integrated
    git support (below). It can run both `.py` files with `# %%` cells and
    Jupyter notebooks.
  - VERSION CONTROL (git): the moment you have a script you're proud of, or
    are collaborating with a studio partner, "final_v3_ACTUALFINAL.py" stops
    working as a versioning strategy. Git tracks every change with a
    message explaining why, and GitHub gives you a free, shareable home for
    your code — genuinely worth a few hours of dedicated learning once you
    have a real project to put under it. Don't learn git in the abstract;
    learn it ON your first self-directed project from Section 3.

================================================================
6. WHEN YOU GET STUCK
================================================================

This will happen more, not less, as you move off this course's supported
path — that's a sign you're doing something real, not a sign you regressed.

  1. Read the LAST line of the traceback first, exactly like Week 1. It
     almost always names the actual problem; the lines above it are just
     the path that led there.
  2. Reduce the problem before you ask for help — comment out everything
     except the one line that fails, with the smallest input that still
     triggers it. This alone resolves a large fraction of "stuck" moments,
     because writing the minimal failing case usually reveals the bug.
  3. Search the tool's OWN documentation before a general web search, and a
     general web search before an AI assistant, for anything involving a
     library outside this course's core stack — for the reason in Section
     2, the further you are from pandas/NumPy/scikit-learn, the less an AI
     assistant's first answer should be trusted without verification.
  4. If an AI assistant's fix works but you don't understand why, that is
     not a finished task. Ask it to explain the fix in terms of concepts
     you already know from this course (a boolean mask, a merge key, a
     leakage feature) until you could re-derive it yourself. Code you can't
     explain is not code you can maintain, extend, or defend to a critic.

================================================================
7. LAST WORD
================================================================

Fifteen weeks ago, a blank Spyder window and a syntax error were both
intimidating. They mostly aren't anymore. The one predictable thing about
what comes next is that it will intimidate you again — a new library, a
bigger dataset, a tool with worse documentation — and the same four-part
habit (question, assumptions, method, check) that got you through Week 1
is exactly what gets you through that too. Use it on purpose. Good luck.
